# Forerunner 255 19.18 firmware audit

_Scope: the official `19.18.zip` update package and the BLE protocol implemented
in `protocol/` and `app/.../sync/`._

## 1. What the package contains

The supplied `19.18.zip` contains one `gupdate.gsp`. That file is itself a ZIP
with a 520-byte prepended block, followed by the normal central directory:

| Entry | Size | Notes |
|---|---:|---|
| `package.xml` | 67 B | names `bundle.gsp` as the payload |
| `manifest.xml` | 1039 B | product and component versions |
| `bundle.gsp` | 33,492,248 B | opaque Garmin bundle |

`bundle.gsp` starts with `b1 b5 bf 96`, has 7.999994 bits/byte of entropy, and
its length is `8 + 16 × n`. A second package (29.05, downloaded directly from
Garmin) has the same magic and the same alignment but a different 4-byte field
after the magic. This is a fixed header plus block-aligned encrypted payload,
not a GCD/RGN image. There are no readable protocol strings, ELF headers,
ARM vectors, or ZIP/gzip signatures inside it.

Reproduce the container inspection with:

```bash
python3 tools/inspect_gsp.py /path/to/gupdate.gsp
```

### Manifest

```text
part: 006-B3992-10   version 1918
```

| Component | Version | Part |
|---|---:|---|
| host software | 1918 (19.18) | `006-B3992-00` |
| GPS | 1000 (10.00) | `006-B3865-08` |
| ANT/BLE | 6 (0.06) | `006-B3994-00` |
| Sensor Hub | 3020 (30.20) | `006-B3995-00` |
| other component | 360 | `006-D8580-XX` |
| resources (host 1918) | 1918 | `006-D9352-02` |
| other component | 140 | `006-D9456-02` |
| database | 10 | `006-DA389-00` |

The GPS / ANT-BLE / Sensor Hub versions match Garmin's published 19.18 release
notes (GPS 10.00, ANT/BLE 0.06, Sensor Hub 30.20), and `006-B3992` is the
non-Music Forerunner 255. The package is therefore the correct model, not the
255 Music (`006-B3990`) or 255S. The remaining part numbers are resources or
companion components that the manifest does not label.

The `forceVersion 1405` and `nonvolClearVersion 450` fields explain why a
`force.tmp` file is needed when installing this package over a newer firmware:
the package deliberately gates downgrades and clears non-volatile settings.

## 2. What can and cannot be checked from this firmware

Firmware-level checks that **are** possible:

- product identity (`006-B3992`) and host/component versions;
- the platform split (host, GPS, sensor hub, ANT/BLE, resources);
- the absence of any unencrypted protocol descriptor or handler table.

Firmware-level checks that are **not** possible without the device key:

- GATT service/characteristic tables;
- GFDI/Multi-Link dispatch tables;
- GDI/protobuf field numbers and capability masks;
- timing, retry and buffer behaviour.

The bundle is decrypted by the watch bootloader. The Garmin Connect APK contains
no `.gsp`/`bundle.gsp` handling or firmware key (it transfers user files, not
firmware images). Extracting the key would require a bootloader/raw-flash dump
or a device exploit, not the update package.

For comparison, the repository also contains an **unencrypted** Forerunner 245
3.10 GCD. Its `fw_all` image contains the numeric values used by `Gfdi.kt`
(5000, 5002–5005, 5007–5009, 5011/5012, 5024/5026, 5030/5031, 5036/5037,
5043/5044, 5050, 5052, 5054, 5057, 5101), including a dense cluster around
file offset `0x3f35xx` that looks like a dispatch/constant region. That is
consistent with the legacy half of the protocol, but the FR245 predates the GDI
protobuf FileAccess layer and cannot validate it.

The authoritative source for the FR255 GDI path remains Garmin Connect 5.19.1
(`apk/apktool_out`) and the real BLE captures in `captures/`.

## 3. Protocol audit

### Confirmed correct

| Area | Evidence |
|---|---|
| Multi-Link control frames (`0005`, `0000`, `0002`, register response parsing) | `MlControl`, APK `com.garmin.device.multilink`, live captures |
| GFDI `[size][type][crc]` framing, 5-bit sequence encoding | `Gfdi.kt`, `GfdiTest`, captures |
| CRC-16/0x8005 with Garmin nibble table | `Crc16.kt`, documented vectors, captures |
| COBS delimiters/chunking/254-byte runs | `Cobs.kt`, unit tests |
| GDI 14-byte `[id][offset][total][chunk]` header | `GdiFrame`, APK `qX.d`, captures |
| Phone→watch GDI on 5043, replies on 5044, ACK every chunk | `GdiClient`, captured 487-byte item lists |
| Transport-pipe service IDs, configure frame, zlib stream | `TransportPipe`, APK `MLRTransportPipe`, captures |
| Legacy directory/download/CRC/archive flow | `LegacySync`, FR245 reference, captured logs |
| Workout/PacePro `CREATE_FILE` → `UPLOAD_REQUEST` → data → `SYNC_COMPLETE` | `GfdiFileUpload`, `WorkoutUploader`, field-verified on FR255 |
| FIT workout/pace-band encoders | `FitWorkout`, `FitPaceBand`, unit tests |

### Fixed in this audit

1. **DEVICE_INFORMATION reply did not match Garmin Connect.**
   Garmin (`nX.a.g`) answers with protocol `0x96` when the watch reports
   `>= 0x96` (or `0x71` on older watches), its own app version, then
   friendly name / manufacturer / model and a trailing `1`.
   The implementation echoed the watch's protocol (`0x97` on the FR255),
   used `7791` as an app version, repeated the friendly name, and used
   `Android` in the model slot. It now follows the official layout and is
   populated from `Build.MODEL`, `Build.MANUFACTURER` and
   `BuildConfig.VERSION_CODE`.

2. **Legacy workout upload ignored the CRC seed.**
   `UPLOAD_REQUEST` answers with
   `[uploadStatus][dataOffset:u32][maxFileSize:u32][crcSeed:u16]`.
   The uploader logged the seed but started the running CRC at `0`.
   It now seeds the CRC from the watch response. This was harmless only while
   the FR255 returned `0`; other firmware may return a non-zero seed.

### Open differences / risks

1. **CONFIGURATION reply echoes the watch's capability mask.**
   Garmin (`nX.a.onMessageReceived`) builds a host capability set and sends
   `[count][bitmap]`. We echo the watch's full set, which claims support for
   music, weather, LiveTrack, CIQ, SMS and other services we do not implement.
   The watch accepts this and sync works, but a smaller host mask would avoid
   requests the app can only ignore. This needs hardware A/B testing before
   changing, because a wrong mask can suppress a service the sync path needs.

2. **MLR is receive-only reliable.**
   `MlrReceiver` delivers in-order fragments and acknowledges the contiguous
   sequence, but there is no send window, timeout or retransmission of dropped
   outbound fragments. File pulls rely on the watch closing the pipe and on
   `TransferStatusRequest`; workout writes rely on the BLE write queue and the
   pipe close. It has worked on the FR255, but it is not a full MLR
   implementation.

3. **GDI ACKs always report success.**
   Every chunk is acknowledged with `ok=0, code=0`, even when an offset gap or
   duplicate is detected. The official codes include `101 DUPLICATE_PACKET` and
   `102 MISSING_PACKET`. Reporting the real result would make a corrupted
   multi-chunk transfer fail fast instead of reassembling bad data.

4. **`FeatureCapabilitiesRequest`/`Configuration` fields are partly echoed.**
   The request itself matches `GDICore.proto` and `GDIGarminConnect.proto`
   (`client_version`, FileAccess extension 16, GarminConnect extension 11).
   The `CONFIGURATION` payload and `NOTIFICATION_SUBSCRIPTION` reply are still
   byte-for-byte echoes rather than a modelled host configuration.

5. **`DEVICE_INFORMATION.max_packet_size` is ignored.**
   The watch reports it (512 in the captured FR255 packet, 0x0220 in another
   capture). The app uses the BLE MTU for writes and a fixed 340-byte legacy
   upload chunk. This is conservative and works, but it does not derive the
   chunk size from the negotiated watch value.

6. **`AUTH_NEGOTIATION` reply is a fixed five-zero payload.**
   Garmin's real auth handler builds a supported-method bitmask; the stub used
   by devices without PIN auth answers differently. The FR255 accepts the
   zero payload, so this is only a compatibility risk for other models.

7. **Compressed legacy downloads (`5054`) are not implemented.**
   This is already documented for the FR245 path. The FR255 uses GDI, so it
   does not affect the target device.

## 4. Conclusion

The multi-link and GFDI framing, the GDI transport and the legacy upload paths
match the recovered Garmin Connect implementation and the captured FR255
behaviour. The two concrete defects found in this pass were the handshake
identity and the ignored legacy-upload CRC seed; both are fixed and covered by
the protocol test suite.

The firmware package cannot be used to verify the GDI layer further because its
only payload is encrypted. To continue firmware-level work, the next useful
artifact is a bootloader/raw-flash dump from the watch, not another `.gsp`
update package.
